# Learnings

- Task 1 stream abstraction: `StreamData` works cleanly as a frozen dataclass carrying canonical `molar_flow_rate` plus optional thermo metadata (`species_ids`, `phase`, `enthalpy_molar`, `entropy_molar`) and optional `macro_step_time_s` copied from `PortCondition`.
- Conversion behavior is stable when `from_port_condition` prefers `state.species_ids` and falls back to `PortCondition.species_ids`; `to_port_condition` mirrors metadata back into both `MaterialState` and the port wrapper.
- Port attribute naming helper rule implemented as a single shared mapper: only `inlet` maps to base attributes (`flow_rate`, `temperature`, `pressure`, `composition`), while every other port name is prefixed (`{port}_flow_rate`, etc.).
- Correction pass for Task 1: strict plan fidelity requires `StreamData.mole_fractions`, `PortAttributeMap.flow`, no `StreamData.macro_step_time_s`, `default_*_map(port_name)` values using `{port_name}_flow`, and `StreamPortIO` methods without extra mapping arguments.
- Task 2 single-port adaptation pattern: define explicit class-level `_INLET_MAP`/`_OUTLET_MAP` (`PortAttributeMap`) per unit, validate `port_name` against `self.ports` first, then translate via `setattr`/`getattr` without altering existing process equations.
- For Pump/Valve stream I/O conversion, robust mol/s <-> m^3/s requires mass density and molecular weight (`molar_density = density_kg_m3 / (molecular_weight_g_mol / 1000)`), with clear `ValueError` paths when property-package data is unavailable.
- Task 3 multi-outlet adaptation remains non-invasive when each unit declares explicit `_INLET_MAP`/`_OUTLET_MAP` and validates `port_name` against `self.ports` before attribute transfer.
- FlashDrum can satisfy shared outlet T/P stream mapping without new state declarations by exposing an `outlet_pressure` property alias backed by `flash_pressure`.
- ShortcutDistillation outlet stream mapping to `distillate` and `bottoms` is clearer when condenser/reboiler conditions are explicit property-backed attributes used by `_OUTLET_MAP`.
- HeatExchanger dual-stream support is simplest and deterministic with fully explicit maps for `hot_inlet`, `cold_inlet`, `hot_outlet`, and `cold_outlet`.
- Task 4 dynamic-port adaptation for vector-backed units (Mixer/Splitter) works best by validating `port_name` against `self.ports` first, then mapping dynamic `inlet_i`/`outlet_i` names to array indices while preserving existing algebraic state structures.
- Dynamic map helpers (`default_inlet_map`/`default_outlet_map`) can still be used for deterministic naming and error context even when stream values are physically stored in flattened arrays instead of scalar per-port attributes.
- Task 5 reactor stream I/O can keep internal L/s state untouched by converting at the API boundary: `apply_inlet` maps mol/s to L/s via property-package `density` + `molecular_weight`, while `get_outlet_stream` performs the inverse conversion back to mol/s.
- Robust conversion parity with Pump/Valve comes from a shared density-resolution sequence (`flash_tp` liquid density, then vapor density, then `density(...)` fallback) plus strict positive finite validation and explicit invalid-port errors.

- Task 6 hydraulic integration pattern: each unit now exposes `to_hydraulic_element(port_name)` with strict outlet-port validation; multi-outlet units accept their real outlet names and return clear allowed-port lists on invalid names.
- Pump/Valve hydraulic coupling stays physics-backed by reusing native pump pressure-rise callbacks and valve Cv/open-fraction resistance conversion (`calculate_effective_valve_resistance`) through shared hydraulic adapter helpers.
- Added `thermodynamics/hydraulic_adapters.py` to centralize default hydraulic parameters (`delta=1e-6`), per-unit default pipe resistances, and convenience parameter builders for pump/valve integration tests and compile-path reuse.

- Task 6 scope correction: reverted temporary protocol-shape edits in `connection/hydraulic_element.py` and `connection/hydraulic_solver.py`, keeping hydraulic integration fully contained to unit-process adapters/tests.
- Task 7 asymmetric compile-path integration works cleanly by composing an `AsymmetricPortAdapter` from per-outlet square `ProcessBinding` instances, so `ProcessBinding` count invariants stay untouched while 1-inlet/2-outlet units expose real outlet edges.
- `ConnectionNetwork.compile()` can stay on a single architecture path by selecting `ProcessBinding` for equal-port processes and `AsymmetricPortAdapter` only for 1-inlet/multi-outlet processes; unsupported cardinalities still fail early with a deterministic binding error.
- Existing `ThermoBoundaryPropagationStep` outlet routing already supports asymmetric fan-out as long as `get_outlet(port)`/`set_inlet(port, flow)` are available per process binding entry, so no alternate propagation path is required.
- Task 8 auto-wrapping works generically by deriving descriptor `inlet_ports`/`outlet_ports` directly from `unit.ports`, then auto-publishing all ALGEBRAIC and DIFFERENTIAL states from `state_metadata_dict` without per-unit branching.
- Optional runtime-context injection is safest when wrappers call `set_property_package(runtime_context.get_property_package())` only if the unit exposes the setter; units without thermo hooks (for example Splitter) wrap cleanly without errors.
- Task 9 boundary propagation can stay backward-compatible by preferring `StreamPortIO` when available per node (`get_outlet_stream` -> `StreamData` -> `apply_inlet`) and automatically falling back to legacy `ProcessBinding` payload propagation for nodes without stream adapters.
- Feed boundaries fit the current architecture cleanly as explicit `StreamData` maps keyed by boundary id; treating boundary sources as stream emitters lets the same propagation path apply feed streams and unit-to-unit streams uniformly.
- Multi-outlet routing remains generic when propagation resolves streams per edge source port and applies mixed `PortCondition` results back through target `StreamPortIO`, so asymmetric fan-out units (for example FlashDrum) route vapor/liquid streams to distinct downstream targets without special-case plumbing.
- Task 10 flowsheet core can stay on the single connection architecture by building `ConnectionNetwork` with `HydraulicCompileLifecycle`, per-edge hydraulic equations from `unit.to_hydraulic_element(...)`, runtime `bind_stream_port_ios(...)` + `set_feed_streams(...)`, and returning a standard `ConnectedPlantOrchestrator`.
- Port inference is safest when `connect()` normalizes endpoints by role: feeds are source-only boundaries, explicit `unit.port` is validated against declared inlet/outlet tuples, and ambiguous bare unit ids fail with available-port lists.
- Task 11 compile-time validation fits cleanly as a pre-network gate in `Flowsheet.compile()`: fail fast on missing feed boundaries, unbound inlets, and species incompatibilities, while using warnings for dangling outlets, disconnected subgraphs, and recycle cycles to preserve backward-compatible compile behavior for valid configurations.
- Species diagnostics are most actionable when feed and unit metadata are reconciled against `runtime_context.species_registry.cas_list`, then mismatch errors name the specific missing species (common name + CAS) on the failing edge.
- Task 12 results API is most reliable when histories are sampled in `Flowsheet.run()` immediately after each macro-step; this yields deterministic `time_points`, per-unit state traces, and per-connection stream arrays without exposing connection-runtime internals.
- `FlowsheetResults.get_stream(source, target)` is ergonomic when it supports both exact `unit.port` keys and unambiguous bare `unit`/`feed` aliases; ambiguous shorthand should fail with matching connection options.
- Task 12 compatibility fix: keep the new structured fields (`time_points`, `units`, `streams`) while retaining legacy `step_results` on `FlowsheetResults`; populate it from `run()` so Task 10-era assertions keep working unchanged.
- Task 13 demo rewrite stays concise and stable when it uses only `Flowsheet` builder APIs (`add_unit`, `add_feed_from_values`, `chain`, `connect`, `compile`, `run`), explicit `flash.vapor_outlet`/`flash.liquid_outlet` wiring, and `FlowsheetResults.get_unit(...)`/`get_stream(...)` for reporting.
- Sensor/controller installation requirement can be satisfied directly on wrapped systems via `flowsheet.get_system(unit_id)` and `System.add_component(...)` with `SampledDelayedSensor` + `ControlElement(PIDController(...))` before `compile()`/`run()`.
- Task 13 retry fix: meeting the strict total-line gate was easiest by shortening constructor configuration to robust defaults, keeping explicit `flash.vapor_outlet`/`flash.liquid_outlet` wiring and wrapped-system sensor/controller install, and trimming demo structure to 70 total lines.
- Task 14 integration-test pattern: robust controller verification in flowsheet tests is most reliable through `flowsheet._subsystems[unit_id].add_sensor(...)` and `.add_control_element(...)` (subsystem phase execution path), plus a post-run `sensor.update(system.time)` check to assert sensor readings against direct process state values deterministically.
- Task 14 hydraulic+mass-balance validation pattern: assert hydraulic execution via `step_result.runtime_step_result.bookkeeping.executed_sequence` containing `hydraulics_solve`, and compute mass-balance closure on stabilized timesteps (exclude first macro-step warm-up sample where inlet/outlet flow staging can transiently differ).
- Task 14 remediation: to satisfy per-connection mass-balance acceptance robustly over long horizons (>=50 steps), compare each connection stream flow history against its source-side mass reference (feed boundary reference for feed edges; source unit outlet-flow history for unit edges) with `<1e-3` relative error on stabilized samples.
- Task 15 retry #2: the demo line-count gate was satisfied by trimming only non-essential formatting while preserving explicit flash multi-outlet wiring, sensor+controller setup, and compatibility KPI keys (`feed_temperature`, `vapor_flow_mol_s`).

- 2026-03-05 F1 audit learning: structural implementation for Tasks 1-12 is present and consistently wired through `Flowsheet -> ConnectionNetwork -> ConnectionRuntimeOrchestrator -> ConnectedPlantOrchestrator`, with explicit StreamPortIO and hydraulic element hooks across all 12 units.
- 2026-03-05 F1 audit learning: explicit guardrails appear intact in code (`ProcessBinding` unchanged, no separate simple-path orchestrator introduced, demo reduced to 79 lines).
- 2026-03-05 F4 audit learning: scope guardrails can all pass while closure is still blocked by behavior-affecting cardinality constraints; adapter support currently covers equal-cardinality and `1->N`, but not `N->1` compile-path binding (for example Mixer `2->1`).

- 2026-03-05 F4 closure learning: source-edge routing for converging units works without thermo-path changes when `get_outlet(shared_port)` returns the shared payload from one representative bound outlet and `bind_outlets` mirrors the same payload across all per-inlet bindings.
