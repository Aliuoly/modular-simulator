
- Future work item from review: split `HeaterCooler` into more realistic subclasses that behave like actual heat exchangers with interacting hot/cold streams, design attributes such as overall heat-transfer coefficient and/or transport-unit heuristics, and degradation/fouling events over time; current `target_temperature_setpoint` / `duty_setpoint` abstraction is too idealized for this use case.
- Review concern from control-surface audit: `CSTR.reactor_volume_setpoint` is currently modeled as a supervisory setpoint consumed by an internal level-control law, not as a physically direct manipulated variable; future work should decide whether this should instead be represented through indirect flow/valve control or a cascade structure rather than as a sanctioned top-level controlled surface.
- Review concern from pressure-drop audit: current unit models blur three different concepts that should be separated cleanly in one future pass: (1) true hydraulic pressure loss (`ΔP`) from friction/restriction/internals/two-phase flow, (2) externally maintained vessel operating pressure (for example a flash drum held by a backpressure valve / pressure controller on vapor outlet), and (3) idealized supervisory setpoints that are not direct physical actuators. The code currently treats some of these as directly controllable state fields.
- One-pass fix guidance for pressure semantics: define a portfolio rule that `pressure_drop` is either a fixed design/operating parameter or a computed hydraulic consequence, but not a generic direct actuator unless the model explicitly represents a valve/opening/restriction as the manipulated element. For flash systems, distinguish `flash_pressure` as an imposed external operating condition from actual manipulated hardware; if retained, document it as a supervisory/external condition rather than a direct MV. Revisit `flash_temperature_setpoint` under the same rule: keep only for explicitly idealized isothermal flash models with external heat duty assumptions, otherwise remove it as a sanctioned controller-facing surface.
- Review concern from flash-drum audit: `FlashDrum.flash_pressure` is currently exposed as a direct controlled state and `outlet_pressure` is just an alias for it, but the model does not include the actual manipulated hardware that would maintain vessel pressure in reality (for example a backpressure valve / PCV on the vapor outlet). Future one-pass fix should choose one explicit contract: either (a) keep `flash_pressure` only as an imposed external operating condition/supervisory boundary condition and stop treating it as a direct MV, or (b) introduce an explicit pressure-manipulating element/valve abstraction and move controller authority to that physical element instead.
- Review concern from flash-drum audit: `FlashDrum.flash_temperature_setpoint` is only used in `thermal_mode == isothermal`, where the model directly imposes `T` and `P` into the equilibrium flash calculation (`flash_tp`). This is not a physically direct manipulated variable for a bare flash drum; it is only defensible as an idealized isothermal operating condition that assumes external heat exchange/control outside the vessel. Future one-pass fix should either (a) keep it only for an explicitly documented idealized isothermal-flash model and remove it as a generic sanctioned controller surface, or (b) replace it with control authority on actual upstream/downstream thermal equipment and let flash temperature emerge from energy balance plus pressure.
- Review concern from pressure-drop audit: `HeaterCooler.pressure_drop` is currently a direct controlled state used as a free algebraic knob (`outlet_pressure = inlet_pressure - pressure_drop`), but the model does not represent the physical hardware that would actually manipulate pressure loss. In realistic process models, pressure drop is usually a hydraulic consequence (geometry, flow, fouling, phase behavior, restriction) or a fixed design parameter, not a direct MV. Future one-pass fix should align `HeaterCooler.pressure_drop` with the portfolio pressure rule: either demote it to a fixed/configured hydraulic parameter, or introduce an explicit hydraulic/valve/restriction abstraction and move controller authority there. If it is intentionally retained as an imposed surrogate, document it clearly as such and stop treating the noun `pressure_drop` as if it meant the same thing as a true physical actuator.
- Review concern from splitter audit: `Splitter.split_ratios` is currently a direct controlled vector that allocates flow across outlets, but a real splitter usually achieves this indirectly through outlet valves, branch resistances, or downstream flow/pressure control. This makes `split_ratios` a reduced-order allocation surrogate rather than a literal direct actuator. Future one-pass fix should choose one explicit contract: either (a) keep `split_ratios` as an intentionally abstract branch-allocation control surface and document it as such, especially for N-way splitters where it stands in for multiple hidden actuators, or (b) introduce explicit outlet valve / branch hydraulic elements and let split ratios emerge from those physical manipulated variables instead of being commanded directly.
- Review concern from separator audit: `ComponentSeparator.split_fraction_targets` is currently a direct controlled vector specifying species-wise partition targets. This is not a literal physical actuator for most real separators; it is a phenomenological separation-performance surrogate standing in for hidden process drivers such as temperature, pressure, solvent ratio, membrane area/selectivity, rotor speed, or residence time. Future one-pass fix should choose one explicit contract: either (a) keep `split_fraction_targets` only as an intentionally abstract separator-performance target and document that it is not a direct MV, or (b) replace it with physically meaningful manipulated variables for the separator family and let species partition emerge from those operating conditions.
- Review concern from pump audit: `Pump.pressure_rise_setpoint` is a reduced-order surrogate for whatever real actuator changes developed head (for example speed, impeller trim, guide-vane position, or downstream pressure control interaction). It is more defensible than the fake supervisory setpoints because pumps really do manipulate head/pressure indirectly, but the name still skips the physical actuator. Future one-pass fix should decide whether the library wants head/pressure-rise targets as acceptable abstract MVs or whether pump control should be expressed through a more physical actuator such as speed.
- Review concern from PFR audit: `PFR.jacket_temperature_setpoint` is an imposed thermal boundary condition for the jacket side, not a literal actuator inside the reactor model. It is more defensible than flash-drum temperature because jacket utilities are real, but it still assumes hidden utility-side control authority outside the unit. Future one-pass fix should either document it explicitly as an external utility boundary/setpoint or shift controller authority to a modeled utility/heating element if physical direct-MV semantics are required.
- Review concern from shortcut-distillation audit: `ShortcutDistillation.reflux_ratio_setpoint` is not a literal single actuator, but it is a standard reduced-order operating/specification variable in shortcut column models. Future one-pass fix should keep it only if the library accepts high-level operating/specification variables as sanctioned controller surfaces for reduced-order units; otherwise reflux control should be tied to more physical manipulated quantities such as reflux flow, boilup, condenser duty, or reboiler duty in a higher-fidelity column model.
- Review concern from shortcut-distillation audit: `ShortcutDistillation.light_key_distillate_recovery` and `ShortcutDistillation.heavy_key_bottoms_recovery` are currently exposed as direct controlled states, but they are product-recovery specifications rather than literal physical actuators. They directly prescribe how key species partition in the shortcut algebra without any modeled tray hydraulics, internal flows, or utility-side manipulated elements. Future one-pass fix should choose one explicit contract: either (a) keep them only as intentionally abstract shortcut-model specification surfaces and document that they are not direct MVs, or (b) demote/remove them as sanctioned controller-facing surfaces in favor of more physical manipulated quantities whose effect on recovery is emergent.
- Review concern from shortcut-distillation audit: `ShortcutDistillation.reflux_ratio_factor` is currently exposed as a direct controlled state even though it is only a fallback operating-policy parameter used when `reflux_ratio_setpoint <= 0`, where the model computes `R_actual = reflux_ratio_factor * R_min`. That makes it a shortcut-policy/meta-specification knob sitting on top of the shortcut calculation, not a literal actuator. Future one-pass fix should either (a) keep it only as a documented shortcut-policy parameter outside the normal MV portfolio, or (b) remove it from sanctioned controller surfaces and require explicit control over physical manipulated quantities or an explicit reflux-ratio specification surface, but not both.
- Higher-severity architecture concern from pump/hydraulics audit: the flowsheet hydraulic layer currently parameterizes `PumpHydraulicElement` from `Pump.pressure_rise` (`flowsheet._resolve_element_parameters` reads `getattr(source_unit, "pressure_rise", 0.0)`), while the unit model and controller-facing surface use `pressure_rise_setpoint` for the runtime control proxy that drives outlet pressure/temperature and pump energy calculations. That creates a split between the network-side pump-head source and the controller-facing/unit-level pump-head proxy: unless the two fields are kept synchronized deliberately, the hydraulic network responds to one value while unit-level thermodynamics/controllers respond to another. Future one-pass fix must choose one source of truth explicitly: either (a) make network hydraulics consume the runtime controlled pump-head variable, (b) collapse the two fields into one clearly documented abstract actuator, or (c) introduce a more physical actuator such as pump speed and derive both hydraulic and thermodynamic pump behavior from that shared state.
- Higher-severity architecture concern from splitter audit: the current flowsheet hydraulic layer solves per-edge flow rates from pressures and hydraulic elements (`flowsheet._build_hydraulic_system` + `thermo_coupling._resolve_hydraulic_flow`), but the `Splitter` unit also computes and publishes its own `outlet_flows` directly from `split_ratios` and `get_outlet_stream()` exposes those unit-level outlet flows. That creates two competing split authorities: unit-owned branch allocation vs connection/hydraulic-owned branch allocation. Future one-pass fix must choose one contract explicitly: (a) topology/hydraulic-owned split, where branch flow emerges from pressures/valves/resistances and `Splitter.split_ratios` is removed or demoted; (b) unit-owned abstract split, where `Splitter` prescribes outlet branch flows and downstream edges do not independently solve branch allocation hydraulically; or (c) an explicit hybrid reconciliation layer where split targets and hydraulic feasibility are coupled intentionally rather than overlapping implicitly.
