## Context

The current repository already has the architectural pieces for the direction the user wants, but they are split across incompatible abstraction layers. `Pump` and `Valve` unit models mainly act as adapters that return hydraulic elements and bootstrap line attachments during flowsheet compile. `Mixer` computes mixed outlet state as a process model, while lower-level connection/runtime code already has explicit junction topology and junction mixing behavior. `Splitter` is the clearest sign of the mismatch: its own file states that configured `split_ratios` are not used by the physical hydraulic-owned splitter, and its algebraic solve leaves `outlet_flows` at zero while real branch flow is expected to come from line hydraulics. At the same time, the high-level `Flowsheet` path never emits `junction_nodes`, endpoint normalization only recognizes feeds and units, and the current lower-level `JunctionProcess` contract is many-in/one-out only. The parent change `define-canonical-hydraulic-solving-semantics` now establishes that the canonical hydraulic closure is a network solve over node pressures and line flows, that junctions are explicit many-in/many-out hydraulic nodes with one pressure unknown per junction, and that line-installed hydraulic elements own pressure boost and flow throttling. This proposal therefore implements the concrete replacement high-level API that aligns with those canonical semantics.

## Goals / Non-Goals

**Goals:**
- Make junctions (as explicit hydraulic nodes per the canonical semantics) and line-installed hydraulic elements the canonical high-level API for mixing, splitting, pressure boost, throttling, and line heat actuation.
- Remove `Pump`, `Valve`, `Mixer`, and `Splitter` from the supported high-level unit-process surface in this change.
- Keep the replacement API ergonomic enough for hand-authored flowsheets and future drag-and-drop UI construction.
- Add high-level boundary sink support so canonical topology-first examples do not need terminal-outlet caveats.
- Ensure that junction compile and runtime behavior inherit the canonical node-pressure solving, mass-conservation, and hydraulics-first ordering from `define-canonical-hydraulic-solving-semantics`.
- Align curated examples, recycle examples, and diagnostics with the canonical topology-first and network-owned branch-flow model.

**Non-Goals:**
- Redesign the hydraulic solver mathematics or add a new flow-physics family.
- Replace lower-level dynamic reconfiguration APIs that already expose line attachment and junction operations.
- Preserve backward compatibility for the removed wrapper-unit APIs.
- Remove true thermodynamic/process unit operations such as reactors, flash drums, or heat exchangers.


## Decisions

1. Add first-class junction registration to the high-level `Flowsheet` API as explicit hydraulic nodes inheriting the canonical node-pressure and mass-balance semantics.
    - Rationale: the UI/game mental model is already a topology node, the lower-level runtime already has a `JunctionNode` concept and mixing logic, and the canonical semantics now formalize that junctions are one-pressure-unknown-per-junction nodes. The high-level API must expose this canonical contract directly.
    - Alternative considered: keep `Mixer`/`Splitter` as convenience unit wrappers. Rejected because it preserves the abstraction mismatch, hides that split flow is not owned by the unit model, and contradicts the canonical network-owned branch-flow semantics.

2. Define the concrete high-level API around explicit topology methods and an upgraded `connect` call, with all elements inheriting canonical hydraulic semantics (network-owned flows, line-installed hydraulic overlays).
    - Public surface:
      - `Flowsheet.add_junction(junction_id, *, inlet_ports: tuple[str, ...], outlet_ports: tuple[str, ...]) -> None` (creates a hydraulic node with one pressure unknown per junction, inheriting canonical mass-balance semantics from the parent change)
      - `Flowsheet.add_sink(sink_id, *, port_name: str = "inlet") -> None` (boundary sink for product handoff)
      - `Flowsheet.connect(source, target, *, line_id: str | None = None, radius_m: float = 1.0, length_m: float = 1.0, pump: PumpInstall | None = None, valve: ValveInstall | None = None, heat: HeatInstall | None = None) -> LineReference` (creates a connection line with optional line-installed hydraulic elements per canonical semantics)
      - `PumpInstall(id: str | None = None, initial_pump_speed: float = 0.0)` means "install a pump on this line"; `id=None` requests a deterministic autogenerated actuator ID.
      - `ValveInstall(id: str | None = None, minimum_open_fraction: float = 0.0, maximum_open_fraction: float = 1.0, initial_open_fraction: float = 1.0)` means "install a valve on this line"; `id=None` requests a deterministic autogenerated actuator ID.
      - `HeatInstall(id: str | None = None, initial_heat_rate: float = 0.0)` means "install a heat actuator on this line"; `id=None` requests a deterministic autogenerated actuator ID.
      - `LineReference` exposes `line_id`, `pump_id`, `valve_id`, and `heat_actuator_id` so callers can bind runtime control surfaces even when IDs were autogenerated.
    - Endpoint syntax remains `<node_id>.<port_name>`, now extended so `<node_id>` may be a unit, feed, junction, or sink. Bare node IDs continue to auto-resolve only when the role has exactly one valid port.
    - Direction rules remain explicit: feeds may only act as sources, sinks may only act as targets, unit/junction outlet ports may only act as sources, and unit/junction inlet ports may only act as targets.
    - Duplicate junction IDs, duplicate port names, ambiguous bare endpoints, and duplicate line/actuator IDs must fail during flowsheet construction with actionable errors.
    - Alternative considered: add a second multi-step line-configuration API instead of extending `connect`. Rejected because the user explicitly asked for a clean, highly abstracted installation surface.


3. Make connection lines the only canonical home for pump, valve, and heat control elements, per canonical line-owned hydraulic semantics.
    - Rationale: this matches the canonical hydraulic ownership model already established by `define-canonical-hydraulic-solving-semantics` and used by runtime and reconfiguration APIs, and it avoids fake process units whose only job is to attach line metadata.
    - Alternative considered: keep `Pump` and `Valve` as thin units for ergonomics. Rejected because the proposal explicitly aims to remove bloat and the canonical semantics now define line ownership as non-negotiable.

4. Introduce native junction registration in `ConnectionNetwork` and compiled topology so junctions inherit the canonical many-in/many-out node-pressure semantics instead of routing through the current many-in/one-out `JunctionProcess` contract.
    - Rationale: the canonical semantics define junctions as one-pressure-unknown nodes with mass conservation across all connected lines. The current domain contract does not represent many-out junctions, while the topology/runtime layer can. The cleanest replacement path is to add explicit network-side junction specs and compile them into `TopologyGraph.junction_nodes` with separate inlet/outlet port collections, all inheriting the canonical pressure-solving rules.
    - Alternative considered: force the change through `JunctionProcess`. Rejected because it bakes a one-out contract into a topology-first API that needs both merging and splitting, and contradicts the canonical semantics.

5. Model junctions as many-in/many-out topology nodes whose outgoing branch flows remain hydraulic-owned per the canonical network-solve semantics.
    - Rationale: the canonical semantics establish that the connection network is the canonical source of solved line flow rates. The current lower-level runtime already computes junction state from incoming flows, and the hydraulic solver is the right owner of branch flow allocation on outgoing lines.
    - Alternative considered: preserve unit-level split-ratio ownership. Rejected because `Splitter` already does not own the physical branch flows, returning zero outlet-flow placeholders is misleading as a canonical API, and the canonical semantics explicitly define network ownership.

6. Specify junction runtime semantics directly from the existing lower-level behavior and canonical ordering so replacing `Mixer` and `Splitter` does not leave physical behavior ambiguous.
    - Converging junction state uses positive incoming flows only, aligns species to a canonical ordering, computes mixed pressure and temperature from flow-weighted averages, and retains the previous junction state when total incoming flow is at or below the near-zero fallback threshold.
    - Diverging junctions expose one junction state to all outgoing edges; the hydraulic solver, not the junction API, determines branch flow per outgoing line (per canonical network-owned branch-flow semantics).
    - Missing previous junction state or missing required runtime edge data is a runtime error, not a silent fallback.
    - Alternative considered: define only structural topology behavior and leave state semantics implicit. Rejected because replacing `Mixer` without semantic requirements would invite incompatible implementations and contradict the canonical hydraulics-first ordering.

7. Reuse existing low-level line geometry defaults and explicit overlay constraints in the high-level API.
    - Default line geometry is `radius_m=1.0`, `length_m=1.0`, with equation/parameter naming inferred from the generated or explicit `line_id`.
    - Pump + valve on the same line is rejected because the low-level hydraulic manager forbids both overlays together.
    - Heat actuators may coexist with either a pump or a valve because they are tracked separately from hydraulic overlay selection.
    - Alternative considered: hide all geometry/default policy from the spec. Rejected because the replacement API must be testable and deterministic.

8. Remove wrapper-unit exports/usages and replace them with actionable migration guidance plus explicit failure behavior for persisted legacy payloads.
    - Rationale: the user asked for immediate removal, but the repository still needs a clean failure mode for anyone following stale examples or imports.
    - Legacy code that imports removed wrapper units should fail with a clear error pointing to junctions and line-installed controls.
    - Saved process-model payloads or flowsheet artifacts that reference removed wrapper-unit types are intentionally unsupported after this change and must fail load with migration guidance rather than attempt auto-conversion.
    - Existing runtime line-actuator tags remain `actuator/pump/<id>`, `actuator/valve/<id>`, and `actuator/heat/<id>` because those already match the line-owned architecture.
    - Alternative considered: deprecate first and remove later. Rejected per requested migration posture.

9. Reconcile recycle examples and related pending proposal guidance (such as `reject-invalid-recycle-loops`) with the line-installed pump model and canonical semantics.
    - Rationale: the recycle validation change currently needs to depend on line-installed pump metadata; if both changes move forward, the canonical recycle example and validation must use line-installed pressure-boost elements aligned with the canonical network-owned hydraulic model.
    - Alternative considered: ignore the conflict until implementation. Rejected because it would create contradictory proposal guidance and leave the repository without a coherent canonical recycle model.

10. Defer code and example rewrites that depend on the completed public API until `canonicalize-hydraulic-junction-api` has landed all API changes and topology registration updates.
    - Rationale: the `reject-invalid-recycle-loops` and curated-example updates need to use the final public API for junction and line-installed controls; sequencing this as a dependent task ensures no breaking reversals during implementation.
    - Alternative considered: begin code rewrites now. Rejected because the API is not yet stable and early rewrites would need to change again after landing.

## Risks / Trade-offs

- Broad breaking change across examples/imports/tests → Mitigation: explicitly scope the removal, add migration/error guidance, and update the curated example set in the same change.
- Junction ergonomics may still feel too low-level if port naming becomes manual boilerplate → Mitigation: require a high-level API that creates named junctions with predictable inlet/outlet ports and deterministic IDs.
- Replacing `Mixer` semantics with junction semantics can expose subtle differences in pressure/state propagation → Mitigation: specify compile/runtime expectations matching the canonical hydraulics-first ordering and add targeted junction regression tests for converging and diverging cases.
- Saved artifacts or stale imports may break abruptly when wrapper types disappear → Mitigation: specify explicit failure modes and migration messaging instead of silent incompatibility.
- Recycle-loop proposal conflict could leave the repo with competing canonical guidance → Mitigation: make this change's coordination with `reject-invalid-recycle-loops` explicit in this design and ensure sibling proposal updates depend on this API landing.
- Code and example rewrites for curated and recycle cases depend on stable public API → Mitigation: sequence those rewrites as dependent follow-up tasks in `reject-invalid-recycle-loops` and coordinate specs immediately while deferring implementation until the junction/line-element API is complete.

## Migration Plan

1. Extend `ConnectionNetwork`/topology compilation to register and emit junction nodes with explicit inlet/outlet ports, integrating the canonical node-pressure and mass-balance semantics from `define-canonical-hydraulic-solving-semantics`.
2. Add high-level flowsheet support for junction definitions, sink registration, and the upgraded `connect(...) -> LineReference` API with line-installed hydraulic element configuration.
3. Implement junction/runtime validation semantics (including hydraulics-first ordering), deterministic ID generation, and line-overlay rules in the high-level API.
4. Update examples, persistence expectations, and tests to use junctions and line elements, including recycle cases.
5. Remove wrapper-unit exports/usages and replace any remaining entrypoints with clear migration failures or docs.
6. Coordinate with and prepare `reject-invalid-recycle-loops` and curated-example-spec updates so they depend on this API landing before code/example rewrites proceed.
7. If rollback is needed before merge, revert the API removal together with the example/docs updates so the public surface remains internally consistent.

## Open Questions

- None. This proposal intentionally fixes the replacement API shape, many-out junction representation, boundary sink inclusion, legacy-payload behavior, and explicit coordination with sibling changes up front so implementation does not need to infer them.
