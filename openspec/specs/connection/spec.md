# Connection

## Purpose

This capability defines connection behavior in the live topology model: explicit junctions, sink endpoints, line-owned hydraulic elements, compile-time recycle validation, and stable runtime connection semantics.

## Requirements

### Requirement: High-Level Flowsheet Exposes Explicit Junction And Sink APIs
The high-level `Flowsheet` API SHALL expose explicit topology methods `add_junction(junction_id, *, inlet_ports, outlet_ports)` and `add_sink(sink_id, *, port_name="inlet")` so users can model mixing, splitting, recycle merge points, and product handoff directly on the supported topology surface.

#### Scenario: Converging junction compiles as topology junction
- **WHEN** a user calls `add_junction("mix", inlet_ports=("fresh", "recycle"), outlet_ports=("out",))`, connects upstream edges into `mix.fresh` and `mix.recycle`, and connects `mix.out` downstream
- **THEN** the compiled topology contains the named junction as a topology junction node rather than a synthetic unit-process node

#### Scenario: Diverging junction represents hydraulic-owned split
- **WHEN** a user calls `add_junction("split", inlet_ports=("in",), outlet_ports=("product", "recycle"))`
- **THEN** outgoing branch flow is solved by the hydraulic line system and the junction does not require a unit-level `split_ratios` state to allocate branch flow

#### Scenario: Duplicate or ambiguous junction ports are rejected
- **WHEN** a user defines duplicate port names on a junction or uses a bare junction endpoint whose role has more than one valid port
- **THEN** flowsheet construction fails with an actionable error naming the duplicate or ambiguous ports and instructing the user to use explicit `<junction_id>.<port_name>` syntax

#### Scenario: Boundary sink is available in the high-level API
- **WHEN** a curated or user-authored flowsheet needs terminal product handoff
- **THEN** the high-level API can register a sink directly and connect a terminal line to `<sink_id>.<port_name>` without falling back to undocumented terminal-outlet conventions

### Requirement: High-Level Connect API Creates Lines With Installed Elements
The canonical high-level `Flowsheet` API SHALL let users create a connection edge through `connect(...)` and optionally install supported line-owned control elements on that edge through explicit nested install configs, without direct `ConnectionNetwork` mutation calls.

The line-owned actuator namespace (`actuator/pump/<id>`, `actuator/valve/<id>`, `actuator/heat/<id>`) remains the general platform contract for connections, but it is not a distillation-specific seam requirement in this capability.

#### Scenario: Pressure-boost overlay is installed on a connection through the high-level API
- **WHEN** a user calls `connect(source, target, line_id="recycle_line", pump=PumpInstall(id="recycle_pump", initial_pump_speed=120000.0))`
- **THEN** the returned/registered line is compiled with a pump attachment on `recycle_line` and no standalone flow-wrapper unit model is created

#### Scenario: Overlay install with autogenerated actuator identifier is explicit
- **WHEN** a user calls `connect(source, target, pump=PumpInstall(id=None, initial_pump_speed=120000.0))`
- **THEN** the line is compiled with a pump attachment, the returned `LineReference` includes the deterministic autogenerated `pump_id`, and the user did not need to supply that identifier manually

#### Scenario: Flow-control and heat overlays remain line-owned
- **WHEN** a user calls `connect(...)` with `valve=ValveInstall(...)` or `heat=HeatInstall(...)`
- **THEN** the control elements are attached to the connection line rather than represented as standalone flow-wrapper unit models

#### Scenario: Default line geometry is deterministic
- **WHEN** a user creates a connection without overriding geometry
- **THEN** the line is configured with `radius_m=1.0`, `length_m=1.0`, and deterministic default equation/parameter naming derived from the line identifier

#### Scenario: Invalid overlay combinations are rejected
- **WHEN** a user requests both pump and valve overlays on the same connection line
- **THEN** flowsheet construction or compile fails with an actionable error stating that a line cannot install both valve and pump hydraulic overlays

#### Scenario: Heat may coexist with one hydraulic overlay
- **WHEN** a user requests a heat actuator together with either a pump or a valve on the same line
- **THEN** the line compiles with both the requested heat actuator and the single requested hydraulic overlay

### Requirement: Junction And Line Identifiers Remain Usable For UI And Runtime Control
The canonical high-level API SHALL preserve ergonomic access to line and actuator identifiers by generating stable defaults and accepting explicit overrides where needed.

#### Scenario: Default identifiers are deterministic
- **WHEN** a user omits explicit line or actuator identifiers while defining a junction-connected line with installed hydraulic elements
- **THEN** the flowsheet generates deterministic identifiers that remain stable across repeated compile of the same topology

#### Scenario: Explicit identifiers are preserved
- **WHEN** a user supplies explicit line or actuator identifiers while defining a junction or line element
- **THEN** the compiled runtime surface preserves those identifiers for diagnostics and control binding

#### Scenario: Identifier collisions fail early
- **WHEN** a user reuses an existing junction, sink, line, pump, valve, or heat actuator identifier for a different object
- **THEN** flowsheet construction fails before compile with an error that names the duplicate identifier

#### Scenario: Returned line reference exposes generated and explicit identifiers
- **WHEN** a user creates a line with any combination of explicit or autogenerated actuator identifiers
- **THEN** the `LineReference` returned by `connect(...)` exposes the final `line_id`, `pump_id`, `valve_id`, and `heat_actuator_id` values needed for diagnostics and runtime control binding

### Requirement: Directional Endpoint Validation Covers All Node Types
The high-level topology-first API SHALL reject invalid source/target directionality across feeds, sinks, units, and junctions before compile proceeds.

#### Scenario: Feed cannot be a connection target
- **WHEN** a user tries to connect any source into a feed boundary
- **THEN** flowsheet construction fails with an actionable error stating that feeds may only be used as connection sources

#### Scenario: Sink cannot be a connection source
- **WHEN** a user tries to connect from a sink boundary into any downstream endpoint
- **THEN** flowsheet construction fails with an actionable error stating that sinks may only be used as connection targets

#### Scenario: Junction and unit port directionality is enforced
- **WHEN** a user tries to connect from a unit or junction inlet port, or tries to connect into a unit or junction outlet port
- **THEN** flowsheet construction fails with an actionable error naming the invalid endpoint and the allowed port direction

### Requirement: Junction Runtime Semantics Define Supported Mixing And Splitting Behavior
The canonical junction model SHALL define observable runtime state behavior for converging and diverging topologies so supported junction behavior remains explicit and stable.

#### Scenario: Converging junction mixes incoming state from positive incoming flow only
- **WHEN** multiple incoming lines feed a junction and at least one incoming line has positive flow
- **THEN** the junction state is computed from positive incoming flows only, with pressure and temperature mixed by flow-weighted averaging and species aligned to a canonical ordering before mixing

#### Scenario: Near-zero incoming flow uses previous junction state
- **WHEN** total incoming flow at a junction is at or below the near-zero fallback threshold for a runtime step
- **THEN** the junction retains its previous state rather than inventing a new mixed state from effectively zero flow

#### Scenario: Diverging junction propagates one junction state to outgoing edges
- **WHEN** a junction has one or more outgoing edges
- **THEN** outgoing edges observe the junction state while per-edge branch flow remains owned by the hydraulic line solve

#### Scenario: Same junction supports multiple inlets and multiple outlets simultaneously
- **WHEN** a user defines one junction with more than one inlet port and more than one outlet port, connects multiple incoming edges into it, and connects multiple outgoing edges from it
- **THEN** the junction compiles as a single topology node, enforces directionality on all ports, mixes incoming state once for the node, and leaves outgoing branch flows to the hydraulic line solve per edge

#### Scenario: Missing runtime state required for junction evaluation fails loudly
- **WHEN** a runtime step is missing the previous junction state or required edge state/flow data for a defined junction
- **THEN** runtime evaluation fails with an actionable error instead of silently dropping the junction update

### Requirement: Wrapper Unit APIs And Live Wrapper Vocabulary Are Fully Removed
The live non-archive repository SHALL no longer ship, reference, or preserve the lower-level unit-process wrapper models for the deleted topology-wrapper and flow-control-wrapper classes. Supported live guidance SHALL describe only explicit junctions, explicit sinks, line-installed `PumpInstall` / `ValveInstall` / `HeatInstall` elements, supported hydraulic primitives, and the remaining supported unit-process families.

#### Scenario: Live package surfaces no longer preserve wrapper symbols or wrapper-specific import guidance
- **WHEN** a user inspects the live non-archive `unit_processes` package surfaces
- **THEN** the repository does not expose lower-level wrapper modules or wrapper-specific import guidance for those deleted unit-process models

#### Scenario: Live source does not keep wrapper-name dispatch tables or runtime defaults
- **WHEN** a user inspects live serializer/load handling, runtime helper tables, and package exports
- **THEN** live source does not carry wrapper-name lookup tables, wrapper-specific migration strings, or default behaviors keyed by the deleted wrapper model names

#### Scenario: Live tests describe only supported surfaces or synthetic fixtures
- **WHEN** repository tests verify hydraulics, runtime coupling, controller harnesses, or supported process-model behavior
- **THEN** those tests use supported unit families, junction-plus-line-install flowsheet APIs, direct hydraulic primitives, or local synthetic fixtures rather than deleted wrapper model classes or wrapper-name assertions

#### Scenario: Live docs avoid the deleted wrapper-model vocabulary
- **WHEN** a user reads non-archive repository docs
- **THEN** the docs describe the supported topology model without mentioning the deleted lower-level wrapper model names

#### Scenario: Archive history remains the only preserved record of wrapper-model names
- **WHEN** repository history or archived OpenSpec changes need to explain the removed wrapper model vocabulary
- **THEN** that historical record lives only under archived artifacts rather than in the live non-archive repository

### Requirement: Hydraulic Network Solve Computes Node Pressures And Line Flows
The flowsheet hydraulic model SHALL be compiled as a network solve with one signed flow variable per line, one pressure variable per node, one pressure-flow balance equation per line, one mass-balance equation per multi-connection node, and at least one fixed pressure point that grounds each connected subnetwork.

#### Scenario: Connected subnetwork compiles with pressure and flow variables
- **WHEN** a flowsheet contains connection lines linked through junctions, boundary nodes, or unit ports that contribute pressure values to the network
- **THEN** the hydraulic compile path produces one signed flow variable per line, one pressure variable per participating node, and enough equations to make each connected subnetwork fully determined with a known pressure starting point

#### Scenario: Missing pressure reference fails the network solve contract
- **WHEN** a connected subnetwork has pressure variables but no pressure is fixed anywhere in that subnetwork
- **THEN** compile or validation fails with an actionable error explaining that the subnetwork has no fixed pressure point

### Requirement: Canonical Line Equations Are Pressure-Flow Balance Relations
Each canonical connection line SHALL contribute a pressure-flow balance equation based on line resistance together with any active pump or valve hydraulic overlay, while optional line heat overlays remain co-located line metadata rather than replacing the pressure-flow equation.

#### Scenario: Passive line uses resistance-based pressure-flow balance
- **WHEN** a line has only its base hydraulic resistance configuration
- **THEN** the canonical hydraulic equation for that line relates the upstream and downstream node pressures to the signed line flow through a resistance term

#### Scenario: Hydraulic overlay augments the line pressure-flow balance
- **WHEN** a line installs a pressure-boost or flow-control overlay
- **THEN** the canonical line equation remains a pressure-flow balance for that line with the active overlay contribution applied through line-owned hydraulic metadata rather than a standalone unit-process flow equation

#### Scenario: Heat overlay does not change hydraulic ownership
- **WHEN** a line installs a heat actuator together with zero or one hydraulic overlay
- **THEN** the heat actuator remains attached to the line without changing the rule that flow and pressure balance for that line are owned by the hydraulic network solve

### Requirement: Junctions Are Solved As Hydraulic Nodes
The canonical model SHALL solve each junction as one hydraulic network node with one pressure variable per junction and mass conservation across all connected lines, including junctions with multiple inlets and multiple outlets at the same node.

#### Scenario: Multi-in multi-out junction compiles as one hydraulic node
- **WHEN** a flowsheet defines one junction with more than one inlet port and more than one outlet port and connects multiple incoming and outgoing lines to that same junction
- **THEN** the compiled hydraulic system has one pressure variable for that junction, one mass-balance equation covering all connected lines at that node, and one pressure-flow equation for each attached connection

#### Scenario: Junction branch allocation remains network-owned
- **WHEN** multiple outgoing lines leave the same junction
- **THEN** the hydraulic network solve determines the signed branch flow on each outgoing line from the network equations rather than from unit-level split-ratio state or placeholder outlet-flow arrays

#### Scenario: Reverse-flow classification follows solved sign at the junction
- **WHEN** a line attached to a junction reverses sign relative to its declared source-to-target orientation during a runtime step
- **THEN** the junction treats that line as incoming or outgoing according to the solved flow sign relative to the junction node for that step rather than according to the line’s declared endpoint orientation alone

### Requirement: Connection Network Owns Canonical Physical Line Flows
The connection network SHALL be the canonical source of solved physical line flow rates, and unit-process algebraic models SHALL NOT define or override canonical line flows outside the network solve.

#### Scenario: Hydraulic result overrides unit-level flow placeholders
- **WHEN** runtime coupling has both a solved hydraulic result and unit-level flow-like values available for the same connection line
- **THEN** the canonical line flow used for connection transport and downstream branch allocation comes from the hydraulic result

#### Scenario: Removed topology-wrapper placeholders do not define physical branch flow
- **WHEN** a flowsheet contains behavior historically represented by deleted topology-wrapper state such as `split_ratios` or `outlet_flows`
- **THEN** those placeholders are not treated as the canonical source of physical branch allocation for the connected lines

#### Scenario: Solved near-zero hydraulic flow is not silently replaced by unit payload flow
- **WHEN** the hydraulic result includes an explicit solved line flow value that is zero or near zero for a runtime step
- **THEN** runtime preserves that solved hydraulic flow as canonical instead of silently substituting a unit payload flow value for that line

#### Scenario: Fallback flow path is explicit when hydraulic data is missing
- **WHEN** canonical hydraulic data for a line is unavailable during a runtime path that still supports legacy fallback behavior
- **THEN** any non-hydraulic fallback used for transport is explicitly identified by a defined runtime contract and diagnostics rather than being treated as canonical solved line flow

### Requirement: Unit Processes Participate Through Ports And Coupled Relations
Unit processes that participate in hydraulics SHALL do so through one explicit `ProcessModel.hydraulic_participation` contract rather than as implicit standalone flow solvers or inferred metadata-driven participation.

The declaration SHALL name every hydraulically relevant `UnitProcessPorts` port and its role (`passive`, `pressure_state`, or `fixed_pressure_anchor`), the exact pressure state reference used for each port, every flow-balance group the unit contributes to, every pressure relation the unit truly owns, and any unit-owned hydraulic-element coupling that preserves existing `to_hydraulic_element(...)` behavior.

#### Scenario: Unit contributes a hydraulic boundary condition through an explicit declaration
- **WHEN** a unit process exposes a port with fixed pressure, pressure-drop, or other hydraulic boundary information relevant to the network
- **THEN** that information enters the canonical hydraulic solve through an explicit unit hydraulic participation declaration rather than being inferred from field naming conventions alone

#### Scenario: Missing explicit hydraulic declaration fails clearly
- **WHEN** a unit requires fixed-pressure, pressure-drop, or flow-balance participation in the hydraulic network but does not declare that participation explicitly
- **THEN** compile fails with an actionable error identifying the missing unit hydraulic declaration instead of silently inferring canonical behavior from metadata patterns

#### Scenario: Connected unit-process ports require an explicit declaration
- **WHEN** any `UnitProcessPorts` endpoint of a unit is connected into the compiled hydraulic topology
- **THEN** that unit must expose a non-`None` `hydraulic_participation` declaration, even if some or all connected ports are declared passive

#### Scenario: Undeclared ports are not implicitly passive
- **WHEN** a hydraulically participating unit omits one of its declared `UnitProcessPorts` from the `hydraulic_participation` contract
- **THEN** validation or compile fails instead of treating the missing port as implicitly passive

#### Scenario: Balancing groups are the only source of unit flow-balance equations
- **WHEN** a single-path unit, paired-path unit, or branching unit is expected to contribute unit flow-balance equations to the hydraulic solve
- **THEN** those equations come only from explicitly declared flow-balance groups rather than from implicit port-pattern inference

#### Scenario: Ordinary and paired-path units declare their flow-balance groupings explicitly
- **WHEN** a unit has one hydraulic path `(inlet, outlet)` or two independent paired paths such as `(hot_inlet, hot_outlet)` and `(cold_inlet, cold_outlet)`
- **THEN** the unit declares one flow-balance group per hydraulic path and compile does not invent additional pairings from port names alone

#### Scenario: Conflicting explicit declarations fail validation
- **WHEN** one unit hydraulic participation declaration marks a port `passive` while another declaration or relation also treats that same port as `pressure_state`, `fixed_pressure_anchor`, or part of a flow-balance group
- **THEN** model validation or compile fails with an actionable error identifying the conflicting declarations

#### Scenario: Relation and balancing overlap follows fixed rules
- **WHEN** one port is referenced by multiple relation or flow-balance groups
- **THEN** validation allows that overlap only when the port is non-passive, appears in at most one flow-balance group, and each referenced relation uses a valid kind/cardinality for the named ports

#### Scenario: Declared state references may be scalar, indexed, shared, or property-backed
- **WHEN** a unit port uses a scalar pressure state, a vector pressure state entry, or a shared/property-backed scalar pressure accessor
- **THEN** the declaration names that exact state reference explicitly and validation confirms the reference exists and is valid for the instantiated unit instead of relying on name-pattern guessing

#### Scenario: Identical declared pressure references share one compiled pressure variable
- **WHEN** two or more ports in one unit declare the same pressure-state reference
- **THEN** compile maps those ports to the same pressure variable instead of creating a redundant equality relation for that shared state

#### Scenario: Line-overlay hydraulic elements preserve unit-owned hydraulic-element behavior
- **WHEN** a pressure-boost or flow-control overlay participates hydraulically through its existing `to_hydraulic_element(...)` surface
- **THEN** the declaration records that participation as an explicit unit-owned hydraulic-element coupling instead of pretending the model is a simple affine compile-time pressure-offset relation

#### Scenario: Passive unit port is declared explicitly
- **WHEN** a unit port participates in topology but is intended to add no hydraulic boundary condition or pressure-flow relation
- **THEN** the unit declares that port as passive explicitly and the compile path does not invent an additional hydraulic equation for it

#### Scenario: Unknown declaration port fails clearly
- **WHEN** a unit hydraulic participation declaration references a port name not present in the unit's declared `UnitProcessPorts`
- **THEN** model validation or compile fails with an actionable error identifying the unknown port reference

#### Scenario: Direct unit-port fan-in or fan-out requires explicit flow-balance declaration
- **WHEN** multiple lines are attached directly to one unit port without an explicit junction
- **THEN** compile succeeds only if that physical port belongs to the declared flow-balance group that admits the direct attachment; otherwise compile fails with an actionable error telling the model author to insert an explicit junction

#### Scenario: Declared direct multi-edge ports use the flow-balance group equation, not an extra node equation
- **WHEN** a directly attached unit port is admitted by a declared flow-balance group
- **THEN** the hydraulic solve uses the declared flow-balance group continuity equation for that unit context and does not also add a duplicate automatic node mass-balance equation for the same multi-edge process port

#### Scenario: Diagnostics identify the failing unit, port or group, and remediation
- **WHEN** compile or validation rejects a missing, conflicting, or invalid hydraulic participation declaration
- **THEN** the diagnostic names the unit, the offending port or relation/flow-balance group, and whether the remedy is to add `hydraulic_participation` metadata or to insert an explicit junction for unsupported direct multi-edge attachment

#### Scenario: Unit port with pressure_state role uses a deterministic lookup
- **WHEN** runtime or transport logic needs the solved hydraulic pressure for a unit port declared with the `pressure_state` role
- **THEN** it resolves that pressure through the compiled topology's pressure table and the declared port role rather than through string-based name matching or undeclared inference

#### Scenario: Runtime fallback is limited to passive or non-participating endpoints
- **WHEN** runtime pressure or flow lookup finds no compiled hydraulic entry for an endpoint
- **THEN** payload, transport-state, or default fallback is allowed only when the declared participation role says the endpoint is `passive` or outside explicit hydraulic participation; endpoints declared with the `pressure_state` or `fixed_pressure_anchor` role fail instead of silently falling back

### Requirement: Compiled Hydraulics Expose Reliable Lookups For Pressures And Flows
The compiled hydraulic representation SHALL provide reliable lookups from topology identifiers to solved line-flow and node-pressure values so runtime transport, junction mixing, and unit-port coupling do not depend on string-based name matching to find those values.

#### Scenario: Junction pressure is addressable from compiled hydraulics
- **WHEN** runtime needs the solved pressure for a compiled junction node
- **THEN** the compiled hydraulics provide a deterministic way to look up that junction's pressure value from the junction identifier

#### Scenario: Line endpoint pressure is addressable from compiled hydraulics
- **WHEN** runtime needs the solved upstream or downstream pressure associated with a connection line endpoint
- **THEN** the compiled hydraulics provide a deterministic lookup from that endpoint's topology identity to the corresponding solved node pressure

#### Scenario: Canonical line flow is addressable from compiled hydraulics
- **WHEN** runtime needs the solved physical flow for a connection line
- **THEN** the compiled hydraulics provide a deterministic lookup from the line identifier to the corresponding solved signed flow value

### Requirement: Hydraulic Solve Precedes Junction Mixing And State Propagation
Runtime evaluation SHALL resolve canonical hydraulic flows and pressures before thermodynamic junction mixing or downstream state propagation consumes those values.

#### Scenario: Junction mixing uses solved positive incoming flows
- **WHEN** multiple incoming lines feed a junction during a runtime step
- **THEN** the junction mixing logic runs after hydraulic solving and uses the solved positive incoming line flows to determine the mixed state presented to outgoing edges

#### Scenario: Near-zero incoming flow falls back after hydraulic solving
- **WHEN** the hydraulic solve yields a junction total incoming flow at or below the near-zero fallback threshold for a runtime step
- **THEN** runtime keeps the previous junction state for thermodynamic propagation without changing which system owns the hydraulic solve result

#### Scenario: Non-converged hydraulic solve aborts downstream propagation
- **WHEN** the canonical hydraulic solve for a runtime step is singular or returns non-converged
- **THEN** runtime fails the step with actionable diagnostics and does not continue with junction mixing or downstream thermodynamic state propagation from that invalid solve result

### Requirement: Connection Runtime Advances Conserved Process State After Canonical Flow Resolution
For units with substrate-owned conserved holdup, the connection runtime SHALL own canonical boundary-condition application during runtime coupling without delegating that ownership to gameplay code, while the unit process model remains the owner of differential state advance.

#### Scenario: Canonical hydraulic flow drives requested outlet demand
- **WHEN** canonical hydraulic solve and boundary propagation resolve per-inlet transferred conditions and per-outlet requested withdrawal demand for a conserved-holdup unit
- **THEN** the runtime coupling path applies the transferred inlet state plus requested outlet through-flow demand during `connection_runtime_coupling` for consumption on the next `subsystem_process_step` under the existing process-then-runtime phase order
- **AND** gameplay/session code does not inject, overwrite, or mirror those physical boundary conditions.

#### Scenario: Unit process model owns realized outlet state
- **WHEN** a holding tank updates holdup for a macro step
- **THEN** the authoritative holdup advance occurs through the unit’s `ProcessModel.step()` lifecycle rather than a gameplay helper or macrostep-only runtime integrator
- **AND** downstream propagated transfer, runtime inlet/outlet snapshots, and public observability use the tank model’s realized outlet condition rather than the raw requested outlet demand
- **AND** transferable outlet flow over a step never exceeds the withdrawable holdup above the configured near-empty floor.

#### Scenario: Connected plants keep the existing process-then-runtime lifecycle
- **WHEN** a compiled connected plant contains `HoldingTank` or another conserved-holdup unit
- **THEN** the connected plant keeps the existing repo phase order with `subsystem_process_step` advancing the unit model through `process_model.step(duration)` and `connection_runtime_coupling` applying canonical runtime boundary conditions
- **AND** implementation does not add a second post-hydraulic tank-state integrator that would double-advance the same conserved-holdup state in one macro step.

### Requirement: Runtime-Coupled Process State Remains Distinct From The Public Read Model
The runtime SHALL keep conserved process runtime state separate from the public observability snapshot while allowing the public snapshot to project additive read values from that state.

#### Scenario: Persistence and observability stay distinct
- **WHEN** checkpoint persistence captures `process_runtime_state` and public observability exposes `process_state_values`
- **THEN** the observability payload remains a separate consumer-facing read model rather than a direct dump of persistence structures.

### Requirement: Conserved Process Runtime State Round-Trips Through Persistence
Authoritative conserved process runtime state for holding tanks SHALL round-trip through checkpoint/export/restore without rebuilding that state from gameplay mirrors or lossy observability payloads.

#### Scenario: Holding-tank runtime state restores authoritatively
- **WHEN** checkpoint/export captures a runtime that includes holding-tank conserved holdup state and that runtime is later restored
- **THEN** the restored runtime reproduces the authoritative holding-tank process state from `process_runtime_state`
- **AND** later observability reads project from that restored runtime state rather than rebuilding tank state from gameplay-owned mirrors or `observables.process_state_values`.

### Requirement: Invalid Recycle Loops Are Rejected At Compile Time
The high-level `Flowsheet` compiler SHALL inspect all compile-time-detectable directed recycle loops and SHALL reject any loop that lacks supported line-installed pump-based pressure boost with a strictly positive configured initial boost value.

#### Scenario: Recycle loop has no pressure boost
- **WHEN** a flowsheet compile detects a directed cycle and none of the cycle's edges include supported line-installed pump boost metadata with a strictly positive configured initial boost value
- **THEN** compilation fails with a validation error instead of only emitting a warning

#### Scenario: Recycle loop has zero configured pump boost
- **WHEN** a directed recycle loop includes pump metadata but every pump on that loop has a zero configured initial boost value at compile time
- **THEN** the loop is rejected as physically invalid

#### Scenario: Diagnostic identifies invalid loop and remediation
- **WHEN** the compiler rejects an invalid recycle loop
- **THEN** the diagnostic identifies the ordered offending loop path, states that no supported positive line-installed pressure boost was found on that loop, and provides remediation guidance to add a pump or pressure-boosting stage on the recycle path

#### Scenario: Any invalid loop causes compile failure
- **WHEN** a flowsheet contains multiple directed recycle loops and at least one of them lacks supported positive pressure boost
- **THEN** compilation fails even if other loops are valid

### Requirement: Pressure-Boosted Recycle Loops Remain Allowed
The high-level `Flowsheet` compiler SHALL allow a directed recycle loop to proceed when every detected loop satisfies the supported positive line-installed pump-boost rule and all other existing validations pass.

#### Scenario: Recycle loop includes supported boost element
- **WHEN** a detected directed cycle includes at least one supported line-installed pump boost with a strictly positive configured initial boost value
- **THEN** recycle-loop validation passes for that loop and compilation continues normally if no other validation rule fails

#### Scenario: Mixed valid and invalid loops are reported deterministically
- **WHEN** a flowsheet contains one recycle loop with supported positive line-installed pump boost and another recycle loop without it
- **THEN** compilation fails because of the invalid loop and reports the offending loop path(s) deterministically

#### Scenario: Non-cyclic topologies remain unchanged
- **WHEN** a flowsheet topology contains no directed recycle loop
- **THEN** recycle-loop validation does not introduce new compile failures

### Requirement: Dynamic Distillation Column Uses Normal Runtime/Subnetwork Composition
The dynamic distillation-column unit SHALL be composed and stepped through the existing runtime/subsystem/network pathways, not through topology-only placeholders.

#### Scenario: Runtime stepping path is the authoritative behavior surface
- **WHEN** a dynamic distillation column is instantiated in a connected plant runtime
- **THEN** it is stepped through standard subsystem/network orchestration with runtime-owned state evolution
- **AND** behavior is not emulated by topology metadata or inventory-only heuristics.

### Requirement: Multi-Feed Port Connectivity Is Runtime-Authoritative
Connection/runtime wiring SHALL support multiple feed inputs with explicit stage assignment semantics for the dynamic distillation-column unit.

#### Scenario: Multiple connected feeds preserve assigned-stage semantics
- **WHEN** two or more feed streams are connected to the distillation-column unit
- **THEN** each feed’s runtime flow/composition is applied at its configured stage assignment/feed height
- **AND** feed routing is represented in runtime-owned process behavior rather than post-hoc output adjustment.

### Requirement: Distillation Actuation Uses Unit-Local Boundary Requests Without Controller-Binding Claims
Dynamic distillation-column actuation in this change SHALL use unit-local boundary requests for duty and internal return behavior together with explicit external material-routing seams and hydraulic-solved product-withdrawal demand, and SHALL NOT claim controller-bindable distillation control elements in this pack.

#### Governing Equations
- `GE-DA-1` Product-line driving pressure for connected product port `p`:

  `DeltaP_p = P_owner,p - P_dest,p - DeltaP_static,p - DeltaP_minor,p`  `[Pa]`

- `GE-DA-2` Hydraulic-solved outlet demand for connected product port `p`:

  `F_req,p = Psi_line(DeltaP_p, rho_p, mu_p, line_geometry_p)`  `[mol/s]`

  with `F_req,p = 0` when `DeltaP_p <= 0`.

- `GE-DA-3` Unit-local duty requests remain explicit boundary inputs:

  `u_top = condenser_duty_request_W`  `[W]`

  `u_bottom = reboiler_duty_request_W`  `[W]`

- Symbols and assumptions:
  - `P_owner,p` = runtime pressure at the owning unit product port `[Pa]`
  - `P_dest,p` = receiving node or downstream boundary pressure `[Pa]`
  - `DeltaP_static,p` = static-head contribution on the connected line `[Pa]`
  - `DeltaP_minor,p` = connection-line minor/friction loss contribution `[Pa]`
  - `rho_p`, `mu_p` = line-fluid density and viscosity used by the hydraulic solve
  - `Psi_line(...)` = existing connection-network hydraulic flow law family
  - This requirement freezes only that the demand is hydraulic-solved from network state; it does not require a distillation-specific actuator namespace or hidden internal valve law.

#### Scenario: Actuation surfaces remain runtime-owned and line namespace guidance stays general
- **WHEN** condenser duty requests, reboiler duty requests, reflux return, or product routing is actuated
- **THEN** runtime applies unit-local duty requests and hydraulic-solved product-line demand according to `GE-DA-1` through `GE-DA-3`
- **AND** `StagewiseDistillationColumn` uses unit-local boundary request fields for duty and internal return behavior plus explicit external material-routing seams
- **AND** product-line valves, pumps, and other line-owned hydraulic restrictions remain explicit runtime-owned topology rather than hidden distillation-specific valve/head knobs
- **AND** no distillation-specific controller binding contract is introduced by this requirement.

### Requirement: Product Withdrawals Are External Holdup Withdrawals
Distillate and bottoms routing SHALL be wired as external withdrawals from reflux-drum and bottoms-sump holdups, respectively, and any transient mismatch between hydraulic-solved demand and locally realizable withdrawal SHALL be resolved conservatively inside runtime behavior rather than by widening the public actuation surface.

#### Governing Equations
- `GE-PW-1` Owner-holdup withdrawal balance for owner region `o` and component `k`:

  `dM_o,k/dt = F_in,o,k - F_internal,out,o,k + F_internal,in,o,k - F_realized,o * z_o,k`  `[mol/s]`

- `GE-PW-2` Accepted-step realizability constraint:

  `M_o,k(t + dt_acc) >= 0` for every withdrawn owner component holdup.

- `GE-PW-3` Preferred mismatch-handling order:

  1. compute `F_req,o` from `GE-DA-1` and `GE-DA-2`
  2. attempt internal substep refinement down to bounded `dt_sub >= dt_min`
  3. if `GE-PW-2` still fails, set

     `F_realized,o = min(F_req,o, F_withdrawable,o(dt_sub))`

- `GE-PW-4` Withdrawable flow bound over the accepted internal step:

  `F_withdrawable,o(dt_sub) = M_withdrawable,o(dt_sub) / dt_sub`  `[mol/s]`

- Symbols and assumptions:
  - `M_o,k` = owner-region component holdup `[mol]`
  - `F_realized,o` = realized liquid withdrawal from owner region `o` `[mol/s]`
  - `z_o,k` = owner-region liquid withdrawal composition
  - `dt_acc` = accepted macro-step duration
  - `dt_sub` = internal refined substep used to test realizability
  - `dt_min` = bounded minimum internal refinement step
  - `M_withdrawable,o(dt_sub)` = physically withdrawable owner holdup over `dt_sub`
  - This requirement freezes the conservative runtime behavior order; it does not widen any public demand-override API.

#### Scenario: Product withdrawal connectivity is explicit
- **WHEN** product lines are connected in runtime
- **THEN** distillate and bottoms withdrawal follow the explicit external-holdup routing and owner-balance form defined by `GE-PW-1` through `GE-PW-4`
- **AND** distillate flow is withdrawn from reflux-drum holdup through explicit product-line seams
- **AND** bottoms flow is withdrawn from bottoms-sump holdup through explicit product-line seams
- **AND** both withdrawals remain liquid-phase and bounded by available owner holdup
- **AND** withdrawal behavior is not represented as implicit internal sink terms detached from external routing.

#### Scenario: Temporary demand-realizability mismatch stays conservative
- **WHEN** an accepted runtime step temporarily encounters hydraulic-solved product-line demand greater than the owning reflux drum or bottoms sump can physically realize for that step
- **THEN** runtime resolves the step according to `GE-PW-2` through `GE-PW-4`
- **AND** runtime does not overdraw owner holdup or create component moles to satisfy the line demand
- **AND** any safeguard remains internal runtime behavior rather than a new public demand override API.

### Requirement: Ratio Fields Are Not Runtime Actuation Interfaces
Connection/runtime wiring SHALL treat `reflux_ratio` and `boilup_ratio` as initialization/reference/derived-observable semantics only.

#### Scenario: Runtime actuation does not bind ratio knobs
- **WHEN** runtime actuation interfaces are enumerated for dynamic distillation behavior
- **THEN** actuation interfaces are explicit unit-local boundary request fields plus external material-routing seams
- **AND** any exposed `reflux_ratio`/`boilup_ratio` values are derived telemetry from actual runtime flows
- **AND** `reflux_ratio`/`boilup_ratio` are not required as live actuator bindings.

### Requirement: Topology-Only Starts Do Not Qualify As Dynamic-Column Runtime Exposure
Starts that remain topology-only SHALL continue to exclude the distillation-column item from public runtime-supported build surfaces.

#### Scenario: Existing topology-only gameplay remains excluded
- **WHEN** current topology-only starts are inspected in this change
- **THEN** they do not claim dynamic distillation-column runtime behavior
- **AND** they keep existing hide/reject gating for `place_shortcut_distillation_column`.
